Architektura Frontendowa — Porównanie

A: Razor + jQuery vs B: Razor + HTMX + Alpine.js

Kuchnia u Cygana · ASP.NET MVC 8 · Maj 2026

1. Wprowadzenie — o co chodzi?

Obydwa podejścia używają tych samych kontrolerów MVC i Razor Views po stronie serwera. Różnica leży w tym, jak obsługujemy interaktywność po stronie przeglądarki.

Opcja A Razor + jQuery

Klasyczne podejście: serwer generuje pełną stronę HTML, przeglądarka wyświetla. Gdy użytkownik kliknie — pełne przeładowanie strony lub ręczny AJAX z jQuery.

Prostymi słowy: każda akcja = nowa strona. Chcesz dynamiczności? Pisz $.ajax() ręcznie.

Opcja B Razor + HTMX + Alpine.js

Ten sam Razor, ale z HTMX — biblioteką (14 KB), która pozwala aktualizować fragment strony bez przeładowania, używając atrybutów HTML. Alpine.js (15 KB) dodaje lokalną reaktywność (show/hide, toggle, modals).

Prostymi słowy: HTML sam mówi "pobierz ten kawałek i wstaw tu" — bez pisania JS.

💡 Ważne: obydwie opcje NIE wymagają zmian w backendzie. Kontrolery, serwisy, repozytoria, DTOs, walidatory — wszystko zostaje tak samo. Różnica dotyczy wyłącznie tego, co dzieje się w przeglądarce i jak widoki (.cshtml) są napisane.

2. Architektura — jak płyną dane?

Opcja A: Razor + jQuery — cykl żądania

Użytkownik klika "Pokaż plan produkcji na 05.05" │ ▼ ┌─────────────────────────────────────────────────────┐ │ Przeglądarka wysyła GET /Production/Index?date=... │ │ (pełne żądanie HTTP — cała strona) │ └──────────────────────┬──────────────────────────────┘ ▼ ┌─────────────────────────┐ │ ProductionController │ │ .Index(date) │ │ → View("Index", model)│ └─────────┬───────────────┘ ▼ ┌──────────────────────────────┐ │ Razor renderuje PEŁNĄ stronę│ │ (_Layout + Index.cshtml) │ │ ~50 KB HTML │ └──────────┬───────────────────┘ ▼ Przeglądarka wyrzuca stary DOM, parsuje nowy HTML, ładuje CSS/JS, renderuje od zera. ⏱️ Czas: ~300-500ms (pełny reload)

Przy AJAX (jQuery) flow jest inny, ale wymaga ręcznego kodu JS:

$.ajax({ url: '/Production/PlanItems?date=2026-05-05', success: function(html) { $('#plan-table').html(html); // ← ręczne wstawienie } }); // Trzeba też obsłużyć: loading, błędy, CSRF token, animacje...

Opcja B: Razor + HTMX — cykl żądania

Użytkownik klika "Pokaż plan produkcji na 05.05" │ ▼ ┌─────────────────────────────────────────────────────┐ │ HTMX wysyła GET /Production/PlanItems?date=... │ │ (żądanie AJAX — automatycznie, z nagłówkiem │ │ HX-Request: true) │ └──────────────────────┬──────────────────────────────┘ ▼ ┌──────────────────────────┐ │ ProductionController │ │ .PlanItems(date) │ │ → PartialView(model) │ ← zwraca FRAGMENT └─────────┬────────────────┘ ▼ ┌──────────────────────────────┐ │ Razor renderuje TYLKO │ │ _PlanItemsTable.cshtml │ │ ~3 KB HTML (sam <tbody>) │ └──────────┬───────────────────┘ ▼ HTMX podmienia TYLKO element z id="plan-table" w istniejącym DOM. Reszta strony nie zmienia się. ⏱️ Czas: ~50-100ms (partial swap)
🔑 Kluczowa różnica architektoniczna W opcji A kontroler zawsze zwraca pełną stronę (View). W opcji B kontroler rozróżnia: jeśli to żądanie HTMX → zwraca fragment (PartialView), jeśli normalne → pełna strona. Jeden kontroler obsługuje oba scenariusze.

4. Partial Views i Renderowanie

Partial View to fragment HTML (bez <html>, <head>, layoutu) — np. sama tabela, sam wiersz, sam formularz. Obydwie opcje je używają, ale w inny sposób.

Czym jest Partial View — prosty przykład

Wyobraź sobie stronę planu produkcji. Ma nawigację, sidebar, nagłówek — i w środku tabelę z pozycjami. Ta tabela to Partial View.

_PlanItemsTable.cshtml (Partial View) 
@* Plik: Views/Production/_PlanItemsTable.cshtml *@
@model IEnumerable<ProductionPlanItemDto>

<table class="table table-hover">
    <thead>
        <tr>
            <th>Posiłek</th>
            <th>Ilość</th>
            <th>Status</th>
            <th>Akcje</th>
        </tr>
    </thead>
    <tbody>
        @foreach (var item in Model)
        {
            <tr id="item-@item.Id">
                <td>@item.MealName</td>
                <td>@item.Quantity</td>
                <td>
                    <span class="badge bg-@item.StatusColor">
                        @item.StatusText
                    </span>
                </td>
                <td>@* Przycisk — różni się w A vs B *@</td>
            </tr>
        }
    </tbody>
</table>

Jak oba podejścia używają tego Partial View?

Opcja A Renderowanie w pełnej stronie

Views/Production/Index.cshtml 
@model ProductionDayViewModel

<h1>Plan produkcji — @Model.Date</h1>

<!-- Filtr daty: zmiana = przeładowanie CAŁEJ strony -->
<form method="get">
    <input type="date" name="date"
           value="@Model.Date"
           onchange="this.form.submit()" />
</form>

<!-- Partial renderowany na serwerze, 
     wklejony w HTML strony -->
@await Html.PartialAsync(
    "_PlanItemsTable", Model.Items)

⚡ Zmiana daty = GET /Production/Index?date=... → cała strona od nowa (~50 KB).

Opcja B Renderowanie fragmentu przez HTMX

Views/Production/Index.cshtml 
@model ProductionDayViewModel

<h1>Plan produkcji — @Model.Date</h1>

<!-- Filtr daty: zmiana = HTMX pobiera 
     TYLKO tabelę, nie całą stronę -->
<input type="date" name="date"
       value="@Model.Date"
       hx-get="/Production/PlanItems"
       hx-target="#plan-table"
       hx-trigger="change"
       hx-swap="innerHTML" />

<div id="plan-table">
    @await Html.PartialAsync(
        "_PlanItemsTable", Model.Items)
</div>

⚡ Zmiana daty = GET /Production/PlanItems?date=... → serwer zwraca sam partial (~3 KB) → HTMX wstawia go do #plan-table.

🔑 Co to znaczy w praktyce? Partial View jest identyczny w obu opcjach — to ten sam plik _PlanItemsTable.cshtml. Różnica: w opcji A partial jest renderowany wewnątrz pełnej strony. W opcji B serwer potrafi zwrócić sam partial jako odpowiedź HTTP, a HTMX wkleja go w odpowiednie miejsce.

Aktualizacja pojedynczego wiersza

Scenariusz: Szef kuchni zatwierdza ugotowanie jednego posiłku. Wiersz tabeli powinien zmienić status z „Gotowanie" na „Ugotowane".

Opcja A jQuery AJAX

<!-- W _PlanItemsTable.cshtml -->
<button class="btn btn-success btn-approve"
        data-id="@item.Id">
    Zatwierdź
</button>

<!-- W site.js -->
$('.btn-approve').on('click', function() {
    var id = $(this).data('id');
    var $row = $('#item-' + id);
    
    $.ajax({
        url: '/Production/Approve/' + id,
        method: 'POST',
        headers: {
            'RequestVerificationToken': 
                $('input[name=__Token]').val()
        },
        beforeSend: function() {
            $row.css('opacity', '0.5');
        },
        success: function(html) {
            $row.replaceWith(html);
        },
        error: function(xhr) {
            alert('Błąd: ' + xhr.responseText);
            $row.css('opacity', '1');
        }
    });
});

📝 18 linii JS na jedną akcję. Trzeba zadbać o: CSRF token, loading state, error handling, event delegation (jeśli tabela się przeładuje, eventy znikają).

Opcja B HTMX atrybut

<!-- W _PlanItemsTable.cshtml -->
<button class="btn btn-success"
        hx-post="/Production/Approve/@item.Id"
        hx-target="#item-@item.Id"
        hx-swap="outerHTML"
        hx-indicator="#item-@item.Id">
    Zatwierdź
</button>

📝 0 linii JS. HTMX automatycznie: wysyła POST, pokazuje loading (CSS klasa htmx-request), podmienia wiersz odpowiedzią serwera. CSRF token dodawany globalnie (raz).

5. Formularze i Walidacja

Formularze to rdzeń aplikacji ERP: przyjęcie dostawy, rejestracja straty, log temperatury. Obydwie opcje korzystają z FluentValidation (serwer) + jQuery Validation Unobtrusive (klient) — to się nie zmienia.

Przykład: Formularz „Przyjmij dostawę" (WarehouseController)

ReceiveDeliveryRequest.cs (DTO — wspólne dla obu) 
public class ReceiveDeliveryRequest
{
    public long StockItemId { get; set; }
    public decimal Quantity { get; set; }
    public DateOnly ExpiryDate { get; set; }
    public string? SupplierBatchNumber { get; set; }
}

// FluentValidation — walidacja serwerowa
public class ReceiveDeliveryValidator 
    : AbstractValidator<ReceiveDeliveryRequest>
{
    public ReceiveDeliveryValidator()
    {
        RuleFor(x => x.Quantity)
            .GreaterThan(0)
            .WithMessage("Ilość musi być > 0");
        RuleFor(x => x.ExpiryDate)
            .GreaterThan(DateOnly.FromDateTime(DateTime.Today))
            .WithMessage("Data ważności musi być w przyszłości");
    }
}

Opcja A Klasyczny formularz POST

<!-- Views/Warehouse/ReceiveDelivery.cshtml -->
@model ReceiveDeliveryRequest

<form asp-action="ReceiveDelivery"
      method="post">

                asp-items="ViewBag.StockItems"
                class="form-select"></select>
        <span asp-validation-for="StockItemId"></span>
    </div>

               class="form-control" />
        <span asp-validation-for="Quantity"></span>
    </div>

    <div class="mb-3">
        <label asp-for="ExpiryDate"></label>
        <input asp-for="ExpiryDate" type="date"
               class="form-control" />

        Przyjmij
    </button>

        "_ValidationScriptsPartial"); }
}

Po submit: POST → redirect → GET (wzorzec PRG). Cała strona się przeładuje. Walidacja kliencka jQuery wyłapie błędy przed wysłaniem.

Opcja B Formularz z HTMX (bez reload)

<!-- Views/Warehouse/ReceiveDelivery.cshtml -->
@model ReceiveDeliveryRequest

<form hx-post="/Warehouse/ReceiveDelivery"
      hx-target="#delivery-result"
      hx-swap="innerHTML">

        <label asp-for="StockItemId"></label>
        <select asp-for="StockItemId"
                asp-items="ViewBag.StockItems"
                class="form-select"></select>

    </div>

    <div class="mb-3">
        <label asp-for="Quantity"></label>
        <input asp-for="Quantity" 
               class="form-control" />

    </div>

    <div class="mb-3">
        <label asp-for="ExpiryDate"></label>
        <input asp-for="ExpiryDate" type="date"
               class="form-control" />
        <span asp-validation-for="ExpiryDate"></span>
    </div>

    <button type="submit" class="btn btn-primary">
        Przyjmij
    </button>
</form>

<div id="delivery-result"></div>

@section Scripts {
    @{ await Html.RenderPartialAsync(
        "_ValidationScriptsPartial"); }
}

Po submit: POST (HTMX) → serwer zwraca partial z potwierdzeniem (np. alert „Przyjęto 5 kg mąki") → HTMX wkleja go do #delivery-result. Strona nie przeładowuje się. Formularz można wyczyścić eventem htmx:afterRequest.

⚠️ Ważne: jQuery Validation działa w obu opcjach identycznie. HTMX nie wysyła formularza, dopóki jQuery Validation go nie „przepuści". Są w pełni kompatybilne — HTMX przechwytuje submit po walidacji.

Co się dzieje przy błędzie walidacji serwerowej?

ScenariuszAB
Walidacja kliencka (data pusta) jQuery blokuje submit jQuery blokuje submit (tak samo)
Walidacja serwerowa (ilość > stan) Redirect do formularza z ModelState errors → pełny reload Serwer zwraca partial z formularzem + błędy → HTMX podmienia formularz bez reload
Sukces Redirect GET → pełna strona „Dostawy" Serwer zwraca partial z potwierdzeniem → wklejony inline

7. Wzorce Kontrolerów

To kluczowa sekcja — bo kontroler to jedyne miejsce, gdzie opcja A i B różnią się po stronie C#. Różnica jest niewielka, ale ważna.

7.1 Kontroler w Opcji A — klasyczny MVC

ProductionController.cs — Opcja A 
public class ProductionController : Controller
{
    private readonly IProductionService _productionService;

    public ProductionController(IProductionService productionService)
        => _productionService = productionService;

    // GET /Production?date=2026-05-05
    // Zawsze zwraca PEŁNĄ stronę z layoutem
    public async Task<IActionResult> Index(DateOnly? date)
    {
        var planDate = date ?? DateOnly.FromDateTime(DateTime.Today);
        var plan = await _productionService.GetPlanAsync(planDate);

        return View(new ProductionDayViewModel
        {
            Date = planDate,
            Items = plan.Items
        });
    }

    // POST /Production/Approve/42
    // Po zatwierdzeniu: redirect na pełną stronę
    [HttpPost]
    [Authorize(Roles = "Kitchen,Admin")]
    public async Task<IActionResult> Approve(long id)
    {
        await _productionService.ApproveCookingAsync(id);
        return RedirectToAction("Index");
        // ↑ Przeładowuje całą stronę
    }
}

Prosty wzorzec: każda akcja → View() lub RedirectToAction(). Nie ma rozróżnienia między typami żądań.

7.2 Kontroler w Opcji B — dual response (pełna strona LUB fragment)

ProductionController.cs — Opcja B 
public class ProductionController : Controller
{
    private readonly IProductionService _productionService;

    public ProductionController(IProductionService productionService)
        => _productionService = productionService;

    // GET /Production?date=2026-05-05
    // Pełna strona (pierwszy render lub bezpośredni URL)
    public async Task<IActionResult> Index(DateOnly? date)
    {
        var planDate = date ?? DateOnly.FromDateTime(DateTime.Today);
        var plan = await _productionService.GetPlanAsync(planDate);

        return View(new ProductionDayViewModel
        {
            Date = planDate,
            Items = plan.Items
        });
    }

    // GET /Production/PlanItems?date=2026-05-05
    // Nowa akcja — zwraca TYLKO fragment HTML
    // HTMX wywoła tę akcję przy zmianie daty
    public async Task<IActionResult> PlanItems(DateOnly date)
    {
        var plan = await _productionService.GetPlanAsync(date);
        return PartialView("_PlanItemsTable", plan.Items);
        // ↑ Zwraca sam <table> bez layoutu
    }

    // POST /Production/Approve/42
    // Zwraca zaktualizowany WIERSZ (nie całą stronę)
    [HttpPost]
    [Authorize(Roles = "Kitchen,Admin")]
    public async Task<IActionResult> Approve(long id)
    {
        var item = await _productionService.ApproveCookingAsync(id);
        return PartialView("_PlanItemRow", item);
        // ↑ Zwraca sam <tr> — HTMX podmieni ten wiersz
    }
}

Wzorzec: Index() zwraca pełną stronę. Dodatkowe akcje (PlanItems, Approve) zwracają PartialView() — fragmenty HTML, które HTMX wkleja w DOM.

🔑 Kluczowa różnica w kodzie C# Opcja B wymaga dodatkowych akcji w kontrolerze — takich, które zwracają PartialView(). To ~3-5 linii C# ekstra per akcja. Nie jest to duży koszt, ale trzeba o tym wiedzieć — każda interakcja HTMX potrzebuje swojego endpointu.

7.3 Uniwersalny kontroler (działa z A i B jednocześnie)

Jeśli chcesz, aby kontroler obsługiwał oba scenariusze (przeglądarka bez HTMX → pełna strona, HTMX → fragment), użyj sprawdzenia nagłówka:

Wzorzec uniwersalny 
// Metoda pomocnicza (w BaseController lub extension method)
private bool IsHtmxRequest 
    => Request.Headers.ContainsKey("HX-Request");

// Jedna akcja obsługuje oba scenariusze:
public async Task<IActionResult> Index(DateOnly? date)
{
    var planDate = date ?? DateOnly.FromDateTime(DateTime.Today);
    var plan = await _productionService.GetPlanAsync(planDate);
    var model = new ProductionDayViewModel
    {
        Date = planDate,
        Items = plan.Items
    };

    if (IsHtmxRequest)
        return PartialView("_PlanItemsTable", model.Items);

    return View(model);
}

// POST — po zatwierdzeniu
[HttpPost]
public async Task<IActionResult> Approve(long id)
{
    var item = await _productionService.ApproveCookingAsync(id);

    if (IsHtmxRequest)
        return PartialView("_PlanItemRow", item);

    return RedirectToAction("Index");
}

Dzięki temu ten sam kontroler działa z opcją A (redirect) i B (partial swap). Nagłówek HX-Request jest automatycznie dodawany przez HTMX.

9. Problemy i Obejścia

Żadne rozwiązanie nie jest idealne. Poniżej realne problemy, na które natrafisz w projekcie cateringowym — i jak je rozwiązać w każdej opcji.

9.1 Drag & drop w kompletacji (PackingController)

Magazynier przeciąga pozycje między kolumnami „Do spakowania" → „Spakowane". To złożona interakcja UI.

A Problem i obejście

jQuery UI Sortable lub SortableJS. Trzeba napisać ~50 linii JS: inicjalizacja, obsługa drop, AJAX POST z nową kolejnością.

✅ jQuery UI jest naturalnym wyborem

B Problem i obejście

HTMX nie obsługuje drag & drop natywnie. Rozwiązanie: użyj SortableJS (8 KB, bez jQuery) + trigger HTMX po zakończeniu:

<div id="packing-board"
     x-data
     x-init="Sortable.create($el, {
         onEnd: function(e) {
             htmx.ajax('POST', 
                 '/Packing/Reorder', 
                 { target: '#board',
                   values: { 
                       order: getOrder() 
                   }
                 });
         }
     })">

✅ Działa, ale wymaga ~15 linii JS (jedyny wyjątek od „0 JS")

9.2 Mapa tras (LogisticsController)

Moduł 4 wymaga mapy z pinami adresów dostaw i narysowaną trasą.

Identyczne w obu opcjach: Leaflet.js (open-source, 40 KB) z OpenStreetMap tiles. To samodzielny widget JS — niezależny od jQuery ani HTMX. W obu opcjach trzeba napisać ~30 linii JS na inicjalizację mapy.

<!-- Identyczne w A i B -->
<div id="map" style="height: 500px"></div>

<script>
var map = L.map('map').setView([52.23, 21.01], 12);
L.tileLayer('https://{s}.tile.openstreetmap.org/...').addTo(map);
// piny z @Model.Stops — generowane Razorem
@foreach (var stop in Model.Stops)
{
    <text>
    L.marker([@stop.Lat, @stop.Lng])
     .addTo(map)
     .bindPopup("@stop.ClientName");
    </text>
}
</script>

9.3 Event delegation — utracone eventy po AJAX

W opcji A, gdy jQuery AJAX podmieni fragment DOM, eventy (.on('click', ...)) przypisane do starych elementów przestają działać.

A Problem

❌ Trzeba użyć event delegation:

// ŹLE — nie zadziała po AJAX reload
$('.btn-approve').on('click', fn);

// DOBRZE — delegacja na rodzica
$(document).on('click', 
    '.btn-approve', fn);

To częsty błąd juniorów — łatwo o niego zapomnieć.

B Brak problemu

✅ HTMX nie ma tego problemu — atrybuty hx-* są na elementach HTML, więc po podmianie DOM nowe elementy mają swoje atrybuty. Alpine.js inicjalizuje się automatycznie na nowych elementach (x-data).

9.4 Stripe Checkout (CartController)

Klient płaci za zamówienie — integracja Stripe Checkout.

Identyczne w obu opcjach: Stripe.js Elements to niezależny widget — osadzony w <iframe>, nie zależy od jQuery/HTMX. Formularz płatności jest zawsze izolowany przez Stripe ze względów bezpieczeństwa PCI.

9.5 Real-time alerty (temperatury, braki magazynowe)

System powinien wyświetlać powiadomienia w czasie rzeczywistym — np. „Temperatura w lodówce #2 przekroczyła 8°C".

A SignalR + jQuery

// W site.js
var conn = new signalR
    .HubConnectionBuilder()
    .withUrl("/hubs/alerts")
    .build();

conn.on("NewAlert", function(msg) {
    // Ręczne tworzenie HTML
    var html = '<div class="alert">'
        + msg.text + '</div>';
    $('#notifications').prepend(html);
});
conn.start();

B SignalR + HTMX SSE

<!-- Użyj HTMX extension SSE
     lub SignalR + OOB swap -->
<div id="notifications"
     hx-ext="sse"
     sse-connect="/alerts/stream"
     sse-swap="message"
     hx-swap="afterbegin">
</div>

<!-- Serwer wysyła gotowy HTML:
     <div class="alert">...</div>
     HTMX wkleja go automatycznie -->

Alternatywnie: SignalR hub + 5 linii JS, które wywołują htmx.ajax() po otrzymaniu sygnału.

10. Ocena Końcowa

10.1 Kiedy wybrać Opcję A?

  • Zespół nie chce uczyć się niczego nowego — jQuery jest znany od lat
  • Projekt jest bardzo prosty — kilka formularzy CRUD, brak dashboardów ERP
  • Interaktywność nie jest priorytetem — pełne przeładowania strony są akceptowalne
  • Istniejący kod jQuery — migracja byłaby zbyt kosztowna
  • Prowadzący/firma wymaga jQuery — wymóg formalny projektu

10.2 Kiedy wybrać Opcję B?

  • Aplikacja ERP z wieloma interakcjami — dashboardy, zatwierdzanie, filtrowanie w czasie rzeczywistym
  • Zespół zna C# lepiej niż JS — logika w Razor zamiast jQuery
  • Chcesz mniej kodu JS — mniej bugów, łatwiejsze utrzymanie
  • UX ma znaczenie — użytkownicy ERP pracują 8h dziennie, każdy reload irytuje
  • Ograniczony czas — HTMX jest szybszy w implementacji niż ręczny AJAX

10.4 Werdykt

Opcja A: Razor + jQuery

5.75 / 10

Solidna, sprawdzona, ale przestarzała.

Idealna, jeśli celem jest szybkie dostarczenie MVP bez uczenia się nowych narzędzi. Jednak przy 5 modułach ERP, ~1000 linii jQuery AJAX stanie się trudne do utrzymania.

Opcja B: Razor + HTMX + Alpine.js

7.50 / 10

Nowoczesna ewolucja MVC — bez rewolucji.

Daje 80% interaktywności SPA przy 20% kosztu. Wymaga ~2h nauki HTMX i dodania 2 plików. Trade-off: więcej partiali Razor, ale za to prawie zero JavaScript.

Opcja B daje lepszy UX przy mniejszym nakładzie JS.
