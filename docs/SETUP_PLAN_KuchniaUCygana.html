00

Zanim zaczniesz — decyzje których zmiana boli

Te cztery decyzje musisz podjąć zanim ktokolwiek napisze linijkę kodu. Późniejsza zmiana kosztuje godziny.

DecyzjaWybórDlaczego
Gdzie leży .sln? W katalogu głównym repo (nie w src/) Visual Studio domyślnie szuka .sln na poziomie, który otwierasz. Umieszczenie w root eliminuje problemy z ścieżkami przy klonowaniu.
Gdzie leży docker-compose.yml? W katalogu głównym repo (nie w docker/) docker compose up działa natychmiast po wejściu do repo. Dockerfile może być w docker/, compose musi być na górze.
Czy projekt i solucja są razem? Solucja w root, projekty w src/ Separacja kodu produkcyjnego (src/) od testów (tests/) i dokumentacji (docs/) — standard branżowy.
Czy baza danych jest w repo? Nigdy. Plik .db w .gitignore SQLite to plik binarny. W Git zbierałby konflikty przy każdej zmianie danych. Każdy dev ma lokalną kopię; migracje odtwarzają schemat.
🔥
Krytyczne: Niech jedna osoba (Dev 1) zrobi cały bootstrap i wypchnie gotową strukturę do main. Reszta klonuje gotowe repo — nie konfiguruje od zera. To eliminuje 90% problemów na starcie.

Bootstrap — co robi Dev 1 jako pierwszy

DEV 1 wykonuje poniższe kroki przed zaproszeniem reszty zespołu do repo.

  • 1
    Utwórz repo na GitHub
    GitHub → New repository → nazwa: KuchniaUCygana → Private → bez inicjalizacji (bez README, bez .gitignore). Inicjalizacja będzie ręczna żeby mieć pełną kontrolę.
  • 2
    Inicjalizuj lokalne repo
    bash
    mkdir KuchniaUCygana && cd KuchniaUCygana
git init
git branch -M main
# Dodaj remote
git remote add origin https://github.com/TWOJ-USER/KuchniaUCygana.git
  • 3
    Utwórz strukturę katalogów
    bash
    # Katalogi główne
mkdir -p src tests docs docker .github/workflows

# Projekty .NET (puste na razie, VS je wypełni)
mkdir -p src/KuchniaUCygana.Web
mkdir -p src/KuchniaUCygana.Application
mkdir -p src/KuchniaUCygana.Domain
mkdir -p src/KuchniaUCygana.Infrastructure
mkdir -p tests/KuchniaUCygana.Tests

# Placeholder żeby Git śledził puste foldery
touch src/KuchniaUCygana.Web/.gitkeep
touch src/KuchniaUCygana.Application/.gitkeep
touch src/KuchniaUCygana.Domain/.gitkeep
touch src/KuchniaUCygana.Infrastructure/.gitkeep
touch tests/KuchniaUCygana.Tests/.gitkeep
touch docs/.gitkeep
  • 4
    Dodaj pliki konfiguracyjne na poziomie root
    Skopiuj lub utwórz: .gitignore, .editorconfig, stylecop.json, Directory.Build.props, docker-compose.yml, docker/Dockerfile, README.md. Treść z dokumentu architektonicznego.
  • 5
    Pierwsze commit i push do main
    bash
    git add .
git commit -m "chore: initial project scaffold"
git push -u origin main
  • 6
    Utwórz gałąź develop i ustaw ochronę
    bash
    git checkout -b develop
git push -u origin develop
    Następnie w GitHub: Settings → Branches → Add rule dla main i develop.
  • 7
    Zaproś resztę zespołu jako Collaborators
    GitHub → Settings → Collaborators → Add people → wpisz username każdego deva. Rola: Write (nie Admin). Każdy dostanie maila z zaproszeniem.
  • 8
    Utwórz solucję w Visual Studio
    Otwórz Visual Studio → File → New → Project → puste rozwiązanie → lokalizacja: folder repo, nazwa: KuchniaUCygana. VS utworzy KuchniaUCygana.sln w root. Szczegóły w sekcji 04.
  • 9
    Dodaj 4 projekty do solucji
    W Solution Explorer: Add → New Project dla każdego z projektów. Upewnij się że lądują w src/ a testy w tests/. Commit: chore: add solution with project structure.
  • 10
    Zainstaluj NuGet i push do develop
    Zainstaluj wszystkie pakiety NuGet z listy w dokumencie architektonicznym. Ustaw zależności między projektami (Web → Application → Domain ← Infrastructure). Commit + push do develop.

05

Docker i baza danych — co gdzie i dlaczego

✅
SQLite nie potrzebuje kontenera bazy danych. To plik na dysku. Docker jest tutaj tylko do uruchomienia aplikacji webowej — nie do bazy danych jak byłoby z PostgreSQL czy MySQL.

Tryby uruchamiania — kiedy co

TrybKomendaKiedy
Dev lokalnydotnet run w src/KuchniaUCygana.Web/Codziennie podczas rozwoju — najszybszy feedback loop, hot-reload działa
Dev przez Dockerdocker compose up --buildTest że Docker działa, sprawdzenie środowiska produkcyjnego
ProdukcjaCI/CD deploy na Azure/SmarterASPPo merge do main

Gdzie żyje plik .db

ŚrodowiskoLokalizacja pliku .dbKonfiguracja
Dev lokalnysrc/KuchniaUCygana.Web/kuchniaucygana.dbappsettings.Development.json: "Data Source=kuchniaucygana.db"
Docker/app/data/kuchniaucygana.db (w kontenerze) = volume sqlite_datadocker-compose.yml env: ConnectionStrings__DefaultConnection
Azure App Service/home/data/kuchniaucygana.dbApp Service Persistent Storage + env variable

docker-compose.yml — szczegółowy

yaml
# PLIK: docker-compose.yml (NA POZIOMIE ROOT REPO)
version: "3.9"

services:
  web:
    build:
      context: .                     # context = root repo
      dockerfile: docker/Dockerfile  # Dockerfile może być w podfolderze
    container_name: kuchnia_web
    ports:
      - "8080:8080"               # host:kontener
    environment:
      - ASPNETCORE_ENVIRONMENT=Production
      - ASPNETCORE_URLS=http://+:8080
      - ConnectionStrings__DefaultConnection=Data Source=/app/data/kuchniaucygana.db
      - JwtSettings__SecretKey=${JWT_SECRET}     # z pliku .env
      - Stripe__SecretKey=${STRIPE_SECRET}
      - OpenAI__ApiKey=${OPENAI_KEY}
    volumes:
      - sqlite_data:/app/data        # persystuje bazę między restartami
      - uploads_data:/app/wwwroot/uploads
    restart: unless-stopped
    healthcheck:
      test: ["CMD", "curl", "-f", "http://localhost:8080/health"]
      interval: 30s
      timeout: 10s
      retries: 3

volumes:
  sqlite_data:
  uploads_data:

Alternatywa dla DependencyInjection.cs — metody rozszerzające per dev

Zamiast jednego pliku DI dla Infrastructure, każdy dev ma własny plik rozszerzający:

csharp
// Infrastructure/DependencyInjection.cs — wspólny, Dev 1 go tworzy
public static class DependencyInjection
{
    public static IServiceCollection AddInfrastructure(
        this IServiceCollection services, IConfiguration config)
    {
        services
            .AddEcommerceInfrastructure(config)   // Dev 1
            .AddCatalogInfrastructure(config)     // Dev 2
            .AddProductionInfrastructure(config)  // Dev 3
            .AddLogisticsInfrastructure(config)   // Dev 4
            .AddAdminInfrastructure(config);      // Dev 5
        return services;
    }
}

// Infrastructure/EcommerceInfrastructureExtensions.cs — Dev 1 TYLKO tu pisze
public static class EcommerceInfrastructureExtensions
{
    public static IServiceCollection AddEcommerceInfrastructure(
        this IServiceCollection s, IConfiguration c)
    {
        s.AddScoped<IOrderRepository, OrderRepository>();
        s.AddScoped<IAddressRepository, AddressRepository>();
        s.AddScoped<IPaymentService, StripePaymentService>();
        return s;
    }
}

Workflow codzienne — rytm pracy

RANO
Synchronizuj z develop przed pracą
bash
# Zaktualizuj develop (pobierz zmiany innych)

# Po rozwiązaniu:

refactor(production): extract food cost calculator to service
test(orders): add unit tests for OrderService
chore(migrations): add 002_CreateOrdersTable migration

bash

# Gdy feature jest gotowy do integracji → PR do develop

# Reviewer: dowolna osoba z zespołu (nie autor)

git add src/KuchniaUCygana.Infrastructure/KuchniaUCygana.Infrastructure.csproj
